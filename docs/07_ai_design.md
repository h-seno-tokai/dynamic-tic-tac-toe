# 07. CPU / 強化学習の設計

最終更新: 2026-04-29

## 1. 基本方針（確定）

### 1.1 アルゴリズム: AlphaZero系
- **完全教師無し**で学習する（自己対戦のみ）
- Policy + Value 二頭ネットワーク + MCTS（モンテカルロ木探索）
- 学習済みネットを ONNX 形式で書き出し、ブラウザで推論

採用理由:
- ユーザー要件「完全教師無し」と整合（NNUE系は実質的に教師付き）
- Gobblet級の状態空間なら RTX 2080 で家庭用GPU範囲で学習可能
- 1つのネットから複数難易度を派生できる（後述）
- 「AlphaZeroをWebで動かした」というポートフォリオ価値が高い

### 1.2 学習・推論の分離
- **学習**: ローカル（RTX 2080）+ Python + PyTorch
- **配信**: 学習済み重みを ONNX 形式でリポジトリ or 静的ホスティング上に置く
- **推論**: ブラウザ上で ONNX Runtime Web により実行
- **MCTS**: TypeScript で自前実装してクライアント側で動かす

### 1.3 CPU難易度の作り分け方針
1ネットワークを学習し、推論時パラメータで難易度を派生させる：

| 難易度 | チェックポイント | MCTSシミュレーション数 | 温度パラメータ | 想定応答時間 |
|---|---|---|---|---|
| 弱 | 学習初期 or ランダム+浅い探索 | ~50 | 高め（揺らぎ大） | ~1秒 |
| 中 | 学習中期 | ~数百 | 中 | ~3秒 |
| 強 | 最終チェックポイント | ~1000-3000 | 低（最善寄り） | ~10秒 |

最強難易度のみ最終チェックポイントを使う。難易度の段階数はユーザー単独決定事項のため、本テーブルは例示。

## 2. ユーザー決定事項（モデルアーキテクチャ本体）

ユーザーは画像処理を専門とするML技術者。以下はユーザー側で確定する：

### 2.1 入力表現
- 盤面のテンソル化方式（チャンネル数・各チャンネルの意味）
- 例: 駒サイズ × 駒オーナー × 盤面位置 のマルチプレーン表現
- 履歴の含め方（直近Nターン分を含めるか等）

### 2.2 バックボーン
- ResNet系 / 軽量CNN / その他
- 残差ブロック数・チャンネル数・正規化（BN/LN/GN）

### 2.3 ヘッド構成
- Policy head: 出力次元 = 行動空間サイズ（ゲームルール確定後に算定）
- Value head: スカラー（[-1, 1]、勝敗確率）

### 2.4 モデルサイズの目安（参考）
- 重み配信容量とモバイル推論速度の都合上、**数MB以内**を目安に
- GitHub Pages の単一ファイル100MB制限内に収める必要あり

## 3. こちら側で決定する内部仕様（暫定）

### 3.1 学習フレームワーク
- **PyTorch**
- 理由: ONNX エクスポート経路が素直、コミュニティ豊富

### 3.2 推論ランタイム
- **ONNX Runtime Web**
- 理由:
  - PyTorch → ONNX が標準サポート
  - WebGPU / WASM 両バックエンド対応 → モバイル含めて性能を出せる
  - TensorFlow.js より PyTorch との接続が綺麗

### 3.3 MCTS 実装
- **TypeScript で自前実装**
- 探索木はメモリ上のオブジェクトグラフ
- ノードあたり: 訪問回数 N、累積価値 W、事前確率 P、子ノード参照
- UCB1（PUCT）で行動選択、ネットワーク呼び出しはバッチ化を検討

### 3.4 自己対戦インフラ
- Python 側で複数並列に自己対戦実行（multiprocessing）
- リプレイバッファに局面・方策ターゲット・最終結果を蓄積
- 一定ステップごとにネットを更新、新旧で対戦して採用判定

### 3.5 学習〜配信パイプライン
1. Python で学習・チェックポイント保存
2. 採用するチェックポイントを `torch.onnx.export` で ONNX 化
3. opset / dynamic axes を ONNX Runtime Web 互換に
4. 配信先（リポジトリ or 静的ホスティング）に配置
5. クライアントは fetch + ONNX Runtime Web で読込

## 4. 未決事項

- ゲームルール確定後に決まるもの:
  - 盤面サイズ・駒サイズ段階数 → 入力チャンネル数
  - 行動空間の定義 → policy head の出力次元
- 学習ハイパーパラメータ（学習率・バッチ・シミュレーション数など）
- リプレイバッファサイズ・更新頻度
- 旧 vs 新ネットの採用判定基準
- どのチェックポイント群を「弱・中・強」に割り当てるか（学習結果を見て決定）
